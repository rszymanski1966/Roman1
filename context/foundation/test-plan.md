> (§1–§5); cookbook patterns at the bottom (§6) fill in as phases ship.

## 1. Strategy

Tests follow three non-negotiable principles for this project:

1. **Cost × signal.** The cheapest test that gives a real signal for the
   risk wins. Do not promote to e2e because e2e "feels safer." Do not put a
   vision model on top of a deterministic visual diff that already catches
   the regression.
2. **User concerns are first-class evidence.** Risks anchored in "the
   team is worried about X, and the failure would surface somewhere in
   <area>" carry the same weight as PRD lines or hot-spot data.
3. **Risks are scenarios, not code locations.** This plan documents _what
   could fail_ and _why we believe it's likely_ — drawn from documents,
   interview, and codebase _signal_ (churn, structure, test base). It does
   NOT claim to know which line owns the failure. That knowledge is
   produced by `/10x-research` during each rollout phase. If the plan and
   research disagree about where the failure lives, research is the
   ground truth.

Hot-spot scope used for likelihood weighting: `src/`, `supabase/migrations/`, `scripts/` (30 dni do 2026-11-01, 41 commitów).

**Twarde ograniczenie projektu:** żaden test ani bramka nie może wymagać `supabase db reset` ani zmieniać lokalnych danych deweloperskich (wywiad P2, incydent z 2026-10-10). Migracje: `npx supabase migration up`. Testy pgTAP: w transakcji wycofywanej na końcu. Testy TS mogą zapisywać do lokalnej bazy wyłącznie jako konta tymczasowe wąskiego wzorca testowego (`vitest-<runId>-<etykieta>@example.test` oraz zaległe konta smoke `smoke-<13 cyfr>@<domena smoke>` / `smoke-<13 cyfr>-b@<domena smoke>`). Harness usuwa je sweepem przed i po każdym przebiegu i porównuje hash danych deweloperskich (wszystkiego spoza wzorca) przed i po; pozostałe konto wzorca albo zmieniony hash oblewa przebieg (decyzja planu §3 Phase 1, 2026-11-04). Testy migracji piszą wyłącznie do jednorazowych baz wzorca `mig_test_<runId>_<etykieta>` w lokalnym klastrze Postgresa, nigdy do bazy `postgres` z danymi deweloperskimi; harness usuwa bazy wzorca sweepem przed i po przebiegu, a pozostała baza wzorca albo zmieniony hash danych deweloperskich oblewa przebieg (decyzja planu §3 Phase 3, 2026-11-18).

## 6. Cookbook Patterns

How to add new tests in this project. Each sub-section is filled in once
the relevant rollout phase ships; before that, the sub-section reads
"TBD — see §3 Phase <N>."

### 6.1 Adding a unit test

- **Kiedy**: reguła jest czystą funkcją (wejście → wynik, bez bazy, requestu i cookie), np. tryb wyszukiwania, dopasowanie nazwy, stan widoku, URL powrotu. Logikę zaszytą w stronie `.astro` albo endpoincie najpierw wydziel do `src/lib/` bez zmiany wyników, test-first (wzorzec: `src/lib/search-view.ts` wydzielony z `src/pages/ingredients/index.astro`). Reguła zależna od RLS, kaskady albo ograniczeń bazy → §6.2; nagłówki i render → §6.4.
- **Location**: `tests/unit/*.test.ts` (projekt Vitest `unit`). Plik referencyjny: `tests/unit/search-view.test.ts`; dalsze przykłady: `tests/unit/search-match.test.ts`, `tests/unit/list-view.test.ts`.
- **Run locally**: `npm run test:unit` — bez Dockera, bez `npm run dev`, bez harnessu (projekt nie ma global setup, nie tworzy kont). `npm test` uruchamia `unit` razem z `services`. Jeden plik: `npx vitest run --project unit tests/unit/search-view.test.ts`.
- **Granica**: plik w `tests/unit/` importuje tylko testowane funkcje z `@/lib/...` i typy z `@/types`; nigdy `tests/harness/`, klienta Supabase ani pliku `.astro`.
- **Wyrocznia — tabela przykładów**: `it.each` z tabelą wierszy (albo krótkie `it` dla przypadków z wieloma polami wyniku). Każdy wiersz ma komentarz ze źródłem: PRD (`FR-004`), plan zatwierdzonej zmiany z numerem linii (`S-03 :32`) albo „istniejący kontrakt” z plikiem, gdy żaden wymóg go nie nazywa. Oczekiwane wartości to literały (nazwy, tryby, rodzaje stanu, URL-e), nigdy wynik testowanej funkcji ani jej pomocników (`normalizeName`, `toNameKey`, `URLSearchParams`). Nagłówek pliku nazywa ryzyko z §2 i źródła wyroczni.
- **Zawsze**: brak trafień i złe wartości wejścia (nieznany `match`, zły uuid, cudze id), polskie znaki i wielkość liter, nie tylko scenariusze z trafieniem.
- **Przypięte ograniczenie**: zachowanie, które nie jest wymaganiem, ale je utrwalamy, oznacz komentarzem `PINNED CURRENT BEHAVIOUR, NOT A REQUIREMENT` z odnośnikiem do §7 (wiersz NFD w `tests/unit/search-match.test.ts`). Zmiana takiego wiersza to świadoma decyzja, nie poprawka testu.
- **Nie**: mock Supabase, `getViteConfig()`, import strony ani handlera trasy.

### 6.2 Adding an integration test (endpoint + lokalny Supabase)

- **Kiedy**: reguła żyje w serwisie (`src/lib/services/`) i zależy od prawdziwej bazy (RLS, kaskady, ograniczenia). To najtańsza warstwa nad pgTAP, która widzi filtr w TS i mapowanie wyniku (np. 0 wierszy → `not_found`).
- **Location**: `tests/services/*.test.ts` (projekt Vitest `services`). Plik referencyjny: `tests/services/delete.test.ts`.
- **Run locally**: `npx supabase start` (stos musi działać), potem `npm test`; serwer aplikacji niepotrzebny. Jeden plik: `npx vitest run --project services tests/services/delete.test.ts`.
- **Aktor**: `createTestUser("<etykieta>")` z `tests/harness/accounts.ts` zwraca `{ id, email, password, client }`. `client` to supabase-js zalogowany kluczem publishable, więc RLS działa jak w aplikacji. Serwisy przyjmują `SupabaseClient` jako argument: podaj im `user.client`, bez mocków i bez Astro. Etykieta: małe litery, cyfry, myślniki; konto dostaje adres `vitest-<runId>-<etykieta>@example.test`. Drugie konto (cudze id) to drugie wywołanie, np. `createTestUser("delete-other")`.
- **Fixture**: ścieżką użytkownika, jak formularz dodawania: `addSubstitute(user.client, { ingredientName, categoryId, substituteName, ratio, notes, isBest })`. Nazwy unikalne per przebieg (`runId` z harnessu) i świeży fixture w każdym `it`. Kategorie po slugu ze słownika `categories` (seed w migracjach), czytane `adminClient()`. Wspólne pomocniki fixture'ów i obserwacji: `tests/harness/fixtures.ts` (`add`, `loadCategoryIds`, `idsOf`, `oneId`, `pairOf`, `substituteOf`, `bestIdsOf`); nowy plik importuje je stąd zamiast kopiować.
- **Wyrocznia — obserwacja kluczem admina**: `adminClient()` (klucz secret, omija RLS) czyta wiersze konta (`user_id` = id konta) w `ingredients`, `ingredient_categories`, `substitutes` jako posortowane zbiory id, przed i po operacji. Oczekiwane „po” = „przed” minus id, które nazywa reguła (`idsOf` z `tests/harness/fixtures.ts`, w pliku referencyjnym lokalne `accountState`, `without`). Nie licz oczekiwań tym samym zapytaniem co testowany kod; wartość zwracana przez serwis (`{ data, error }`, `code: "not_found"`) to osobna asercja, nie wyrocznia stanu.
- **Zawsze sąsiedzi i brzeg**: asercja obejmuje wiersze, które reguła ma zostawić (zamiennik z tej samej pary, inna para, inny składnik), plus co najmniej jeden brzeg (ostatni wiersz pary, ponowne wywołanie, losowy uuid, cudze konto).
- **Sprzątanie**: test niczego nie usuwa ręcznie. Global setup (`tests/harness/global-setup.ts`) robi sweep przed i po przebiegu; teardown oblewa przebieg, gdy zostało konto wzorca albo zmienił się hash danych deweloperskich (fałszywy alarm, gdy w tym czasie pracujesz w aplikacji). `adminClient()` służy do obserwacji i sweepu, nigdy jako aktor testowanej operacji ani do budowania fixture'ów.
- **Nie**: mock Supabase, `getViteConfig()`, import handlerów tras (endpointy → §6.4), `db reset`.

#### Test współbieżności (dwie sesje Postgresa)

- **Kiedy**: reguła zależy od blokad albo kolejności dwóch równoległych transakcji (`for update`, częściowy indeks unikalny) i istnieje przeplot, w którym poprawna wersja funkcji daje inny wynik niż błędna. pgTAP (jedna transakcja) ani supabase-js (jedno zapytanie na request) tego nie pokażą. Przeplot, w którym obie wersje kończą się tym samym stanem dozwolonym, nie dostaje testu (§7).
- **Location**: `tests/services/<obszar>-concurrency.test.ts` (projekt `services`). Plik referencyjny: `tests/services/best-concurrency.test.ts` (przeploty b i d `set_best_substitute` + kontrola mutacyjna).
- **Run locally**: działający stos (`npx supabase start`), potem `npm test`; jeden plik: `npx vitest run --project services tests/services/best-concurrency.test.ts`. Test łączy się z Postgresem bezpośrednio (`pg`) pod `DB_URL` z `npx supabase status -o env` (`harnessEnv().dbUrl` w `tests/harness/env.ts`). Adres zawiera hasło: nie loguj go i nie wstawiaj do komunikatów błędów.
- **Sesje** (`tests/harness/pg-sessions.ts`): `openUserSession(user.id)` otwiera transakcję jako zalogowany użytkownik (`begin`, `set local role authenticated`, `request.jwt.claims` przez `set_config`, `lock_timeout` 10 s), więc RLS działa jak w aplikacji; `openObserver()` to sesja tylko do odczytu, wyłącznie do `pg_blocking_pids`. Konto i fixture jak wyżej (`createTestUser` w `beforeAll`, `add`), nie przez `pg`.
- **Sterowanie przeplotem**: X wykonuje instrukcję i trzyma blokadę wiersza; instrukcję Y uruchom bez `await` i od razu owiń w `settle(...)` (wynik albo błąd jako obiekt, bez nieobsłużonego odrzucenia); `waitUntilBlockedBy(observer, y.pid, x.pid, 5_000)` odpytuje `pg_blocking_pids`, aż Y czeka na X; dopiero wtedy `commit` X i odczyt wyniku Y. Żadnego `sleep` jako synchronizacji: brak blokady w limicie czasu kończy test czytelnym błędem („Przeplot nie powstał…”), a nie przypadkowym wynikiem.
- **Sprzątanie**: wszystkie sesje w `finally` przez `closeSessions(x, y, observer)`, najpierw sesja trzymająca blokadę (jej rollback zwalnia czekającą).
- **Wyrocznia**: kod błędu Postgresa (`P0002` — nie znaleziono, `23505` — indeks unikalny) albo jawny sukces, plus stan po obserwacji kluczem admina (`bestIdsOf`, istnienie wiersza) jako literalne id fixture'u z zatwierdzonej reguły. Nigdy tekst funkcji ani wynik przepisany z jej SQL.
- **Kontrola mutacyjna** (obowiązkowa): ten sam przeplot przeciw historycznej, błędnej wersji funkcji (w pliku referencyjnym treść bez blokady z `supabase/migrations/20261011201658_best_substitute.sql`) z oczekiwanym fałszywym sukcesem. Mutanta tworzy `openUserSession(user.id, { beforeRole })` w `pg_temp` sesji Y w roli oryginalnej, przed `set local role`; `authenticated` może go wykonać (TEMP i EXECUTE dla PUBLIC), więc działa z tym samym RLS. Nic nie trafia do `public`, funkcja znika z połączeniem. Bez tej kontroli test nie dowodzi, że rozróżnia wersje.
- **Przed zamknięciem zmiany**: plik kilka razy z rzędu bez flaków (Phase 2: 5×) i raz celowo zepsuty (wskaż mutanta w teście głównym → czerwony).

### 6.3 Adding a database test (pgTAP)

- **Location**: `supabase/tests/<obszar>.sql`. Plik referencyjny: `supabase/tests/delete-entries.sql`; najkrótszy szkielet: `supabase/tests/rls-isolation.sql`.
- **Run locally**: `npx supabase test db` (działający stos; uruchamia wszystkie pliki; nie wymaga `db reset`).
- **Szkielet**: `begin;` → `create extension if not exists pgtap;` → `select plan(N);` → setup jako postgres (omija RLS) → asercje → `select * from finish();` → `rollback;`. Nigdy `commit`: wycofanie transakcji gwarantuje, że lokalne dane deweloperskie zostają nietknięte. Po dodaniu asercji zaktualizuj `plan(N)`.
- **Użytkownicy i dane**: wstawiani jako postgres do `auth.users` ze stałymi UUID i e-mailami `@example.test`. Nowy plik bierze własny, nieużywany sufiks UUID (np. `…0000da`/`…0000db` w `delete-entries.sql`, `…0000ea`/`…0000eb` w `edit-entries.sql`; starsze pliki dzielą `…00000a`/`…00000b`), żeby id w wyniku błędu wskazywały plik. Wiersze danych z prefiksem wg tabeli: `1…` składnik, `2…` para składnik–kategoria, `3…` zamiennik.
- **Działanie jako użytkownik**: `set local role authenticated;` + `set local request.jwt.claims = '{"sub":"<uuid>","role":"authenticated"}';` → asercje → `reset role;`. Jako anon: `set local role anon;` + `'{"role":"anon"}'`.
- **Asercje izolacji**: jako B mutacja na wierszu A z `returning id` daje `is_empty` (pusty wynik, nie błąd — na tym opiera się mapowanie „nie znaleziono” w serwisach), a liczności A po próbie są bez zmian; kontrola, że A widzi własne wiersze, dowodzi, że pustka pochodzi z RLS, a nie z braku danych.

### 6.4 Adding a test for a new API endpoint

- **Kiedy**: nowy endpoint albo strona przyjmuje id od klienta (pole formularza, parametr URL). Domyślna odpowiedź na pytanie „jak dodać test dla nowego endpointu z id od klienta?”: dopisz wiersz do tablicy `inputs` w `tests/http/isolation.test.ts` (projekt Vitest `http`); kolejne wejście nie potrzebuje nowego pliku.
- **Run locally**: `npx supabase start` i `npm run dev` w osobnym terminalu, potem `npm run test:http`. Inny adres serwera: `BASE_URL=http://localhost:4321 npm run test:http` (`vitest.config.ts` przekazuje go testom jako `HTTP_TEST_BASE_URL`, bo Vitest nadpisuje `BASE_URL` w workerach). Bez działającego dev przebieg kończy się jednym komunikatem „Uruchom `npm run dev`”.
- **Wzorzec — cudze id ≡ losowy uuid**: dwa konta tymczasowe (`createTestUser`, sesja HTTP przez `signIn` z `tests/http/client.ts`, czyli logowanie formularzem `POST /api/auth/signin`). A ma składnik z kategorią i zamiennikiem, zbudowane `addSubstitute` jako A. Dla każdego wiersza `inputs` B wysyła raz id A, raz świeże losowe uuid. Oczekiwaniem jest odpowiedź dla losowego uuid, nie tekst błędu przepisany z kodu. Test wymaga:
  - tego samego statusu, tego samego `location` po zastąpieniu id znacznikami `<ingredient-id>`/`<substitute-id>`, tej samej treści odpowiedzi, a dla POST także tej samej strony, na którą prowadzi redirect;
  - braku nazw, proporcji i uwag A w czymkolwiek, co dostał B (zdekodowany `location`, treść, strona po redirekcie);
  - wierszy A (odczyt `adminClient()`, wszystkie kolumny) identycznych przed i po próbie;
  - statusu < 500 i braku przekierowania do `/auth/signin` (próba dotarła do kodu jako B).
- **Jak dodać wiersz do `inputs`** (tablica dla `it.each`):
  - POST: `{ name, method: "POST", path, fields: (ids) => ({ <pole_id>: ids.ingredient albo ids.substitute, ...view(ids, kategoria), ...pozostałe pola formularza }) }`. Pola jak w prawdziwym formularzu: z niepełnym formularzem obie próby odbije ta sama walidacja i test przejdzie, nie dotykając id.
  - GET: `{ name, method: "GET", path: (ids) => withQuery("/sciezka", { … }), ownerSees: "<klucz z Secrets>" }`. `ownerSees` to wartość A, którą ta strona pokazuje samemu A; próba kontrolna jako A sprawdza, że ją widać, więc sprawdzenie wycieku może się nie udać.
  - Endpoint z innym rodzajem id: rozszerz `Ids` i fixture w `beforeAll`.
- **Pokrewne wzorce w tym samym katalogu**: mutacja po nazwie zamiast id — `describe` „the same ingredient name in another account” w `tests/http/isolation.test.ts` (osobne konto, nowy własny wiersz, wiersze A bez zmian); ścieżka UI przez stronę potwierdzenia i liczba na niej porównana z obserwacją kluczem admina — `tests/http/delete-confirmation.test.ts`. Serwis pod endpointem z cudzym id: ostatni przypadek w `tests/services/delete.test.ts` (§6.2).
- **Klient Supabase**: nowy endpoint dostaje klienta wyłącznie z `src/lib/supabase.ts` (i obsługuje `null`); `npm run lint:db-access` łamie się przy kluczu service-role/secret albo własnym kliencie.
- **Walidacja** (złe wejście → `?error=` na stronie źródłowej, nie 500): TBD — see §3 Phase 4.

### 6.5 Adding a test for a new migration

- **Kiedy**: każda nowa migracja w `supabase/migrations/`, przed `npx supabase db push`. Nowego pliku testu nie piszesz: bramka sama bierze każdą migrację nowszą niż linia bazowa. Migracja, która zmienia tylko schemat (tabela, indeks, polityka), nie potrzebuje niczego poza zielonym przebiegiem. Migracja zmieniająca dane potrzebuje deklaracji (niżej), a gdy fixture nie ma wierszy, które ona zmienia — także nowych wierszy w fixture. RLS, funkcje i ograniczenia nowej migracji testuje pgTAP (§6.3) albo integracja (§6.2); ta bramka pilnuje danych.
- **Location**: `tests/migrations/migrations.test.ts` (projekt Vitest `migrations`: test dymny, strażnicy linii bazowej i deklaracji, bramka, kontrola mutacyjna, atomowość), `tests/migrations/expectations.ts` (linia bazowa i deklaracje), `tests/migrations/fixture.sql`. Harness: `tests/harness/scratch-db.ts` (jednorazowe bazy, zastępczy `auth`, sweep), `tests/harness/migrate-cli.ts` (`npx supabase migration up --db-url`), `tests/harness/migration-snapshot.ts` (snapshot inwariantów).
- **Run locally**: `npx supabase start`, potem `npm run test:migrations` (ok. 40 s, bez `npm run dev`). `npm test` uruchamia go drugim przebiegiem po `unit` + `services`, nie równolegle (§6.6, Phase 3). Log „migracje pod testem: …” musi wymieniać twoją migrację; pod agentem AI raporter Vitest ukrywa logi zielonych testów: `npx vitest run --project migrations --silent=false`. Kolejność przed pushem na produkcję: README, „Database migrations”.
- **Jak działa**: raz na przebieg powstaje baza `mig_test_<runId>_base`: zastępczy `auth`, migracje ≤ `BASELINE_MIGRATION` przez CLI, potem `fixture.sql`. Każdy przypadek oprócz testu dymnego (ten dostaje własną pustą bazę) dostaje jej klon (`create database … template …`). Bramka nakłada migracje nowsze niż linia bazowa po kolei, tą samą ścieżką co `db push`, i po każdej porównuje snapshot (`toEqual`) z oczekiwanym: bez deklaracji — snapshot sprzed tej migracji, z deklaracją — wynik deklaracji dla snapshotu sprzed niej. Snapshot: `users`, `categories` (slug, nazwa, kolejność), `ingredients`, `assignments` (para ze slugiem kategorii), `substitutes` (z `notes` i `is_best`), `counts` per konto, `ownershipViolations` (zawsze puste). Jawne listy kolumn: nowa kolumna go nie psuje. Błąd CLI oblewa test z wyjściem CLI bez hasła.
- **Linia bazowa**: `BASELINE_MIGRATION` w `tests/migrations/expectations.ts` to ostatnia migracja, która jest już na produkcji (dziś `20261028120000`). Po każdym `db push`: przesuń ją na ostatnią wypchniętą wersję, usuń deklaracje wypchniętych wersji i zaktualizuj `fixture.sql`, jeśli wypchnięte migracje zmieniły schemat jego tabel — w jednym commicie. Strażnicy oblewają przebieg, gdy pliku linii bazowej nie ma w `supabase/migrations/` albo deklaracja dotyczy wersji, która nie jest nowsza niż linia bazowa lub nie ma pliku. `db push --dry-run` ma wymienić dokładnie migracje z logu „pod testem”; starsza na liście znaczy, że linia bazowa wyprzedza produkcję i ta migracja nie przeszła bramki.
- **Fixture** (`tests/migrations/fixture.sql`): dane syntetyczne w kształcie produkcji, wstawiane jako `postgres` (z pominięciem RLS) na schemacie linii bazowej. Stałe UUID w konwencji pgTAP (§6.3): konta `…0000fa`, `…0000fb`, `…0000fc` (konto C bez żadnych wierszy), prefiksy `1…` składnik, `2…` para, `3…` zamiennik z sufiksem `f0NN`, e-maile `@example.test`. Pokrywa: składnik w dwóch kategoriach, wszystkie 3 slugi, pary z najlepszym i bez, `notes` null i niepuste, polskie znaki i wielkość liter, tę samą nazwę u dwóch kont. Nowe wiersze dopisuj z kolejnym sufiksem; test „the fixture covers the cases the migration test relies on” sprawdza pokrycie i liczności literałami, więc zmienia się razem z fixture'em.
- **Deklaracja** (migracja zmieniająca dane): wpis w `expectations` pod wersją z nazwy pliku. Funkcja dostaje snapshot sprzed migracji i zwraca oczekiwany, zbudowany z literałów fixture'u (id, slugi, nazwy), nigdy z wyniku migracji ani przez ponowne wykonanie jej SQL. Zmień każdy klucz, którego dotyka zmiana (usunięcie zamiennika zmienia `substitutes` i `counts`). Brak wpisu = „dane bez zmian”. Przykład dla zmiany nazwy kategorii `ciasta` (wersja przykładowa):

  ```ts
  export const expectations: Expectations = {
    "20261201120000": (before) => ({
      ...before,
      categories: before.categories.map((category) =>
        category.slug === "ciasta" ? { ...category, name: "Ciasta i torty" } : category,
      ),
    }),
  };
  ```

- **Kontrola mutacyjna** (jest w pliku; obowiązkowa przy każdej zmianie snapshotu albo porównania): 6 syntetycznych migracji bez deklaracji (usunięcie zamiennika, przepięcie przypisania przez `category_id`, zdjęcie `is_best`, zmiana `notes` w miejscu, przeniesienie zamiennika na drugie konto przez `user_id`, zmiana nazwy kategorii) musi oblać tę samą funkcję porównania co bramka (`assertAsDeclared`) na oczekiwanym kluczu snapshotu; ta sama zmiana nazwy z deklaracją przechodzi. Nowy inwariant w snapshot = nowy mutant, którego nie łapie żaden inny klucz. Dowód na żywo (np. po zmianie harnessu): tymczasowy `supabase/migrations/<nowa wersja>_probe.sql` z `delete from public.substitutes where id = '30000000-0000-0000-0000-00000000f001'` (wiersz tylko z fixture'u, nieobecny w dev i na produkcji) bez deklaracji → czerwony z różnicą w `substitutes`; potem usuń plik.
- **Atomowość**: przypadek „a migration that fails halfway through its file leaves no trace” przypina zmierzone zachowanie Supabase CLI 2.117.0: plik idzie w jednej transakcji, więc po błędzie w połowie nie zostaje ani zmiana danych, ani nowa tabela, ani wersja w `supabase_migrations.schema_migrations`. Czerwony po aktualizacji CLI to decyzja (§7), nie poprawka asercji.
- **Sprzątanie**: test usuwa tylko własne klony; global setup (`tests/harness/migrations-global-setup.ts`) robi sweep baz `mig_test_` przed i po przebiegu; każdy sweep wypisuje, ile baz usunął (więcej niż 0 po przebiegu = test nie usunął swojej bazy), a teardown oblewa przebieg, gdy po sweepie została baza wzorca albo zmienił się hash danych deweloperskich. Zaległą bazę po twardym przerwaniu usuwa kolejny `npm run test:migrations` (`npm run test:sweep` usuwa tylko konta). Bazy tworzy wyłącznie `createScratchDb` (wąskość wzorca: `tests/harness/scratch-db.test.ts`).
- **Nie**: `db reset` ani próbne `migration up` na bazie deweloperskiej zamiast testu; kopia danych produkcyjnych albo deweloperskich jako fixture (tylko dane syntetyczne); deklaracja przepisana z wyniku migracji; `migration repair` albo `--include-all` w runnerze (test idzie tą samą ścieżką co `db push`); skrypt, który sam robi `db push` (push na produkcję zostaje ręczny). Migracja, która usuwa albo zmienia nazwę kolumny ze snapshotu, wywróci zapytanie snapshotu: `tests/harness/migration-snapshot.ts` zmienia się razem z linią bazową, bez adaptera w deklaracjach. Migracja dotykająca innych części `auth`, `storage` albo rozszerzeń padnie na zastępczym `auth` (§7).

### 6.6 Per-rollout-phase notes

(Po każdej fazie `/10x-implement` dopisuje tu 2–3 linie o tym, czego faza nauczyła.)

**§3 Phase 1 — Izolacja i usuwanie (2026-11-09)**

- Zwykły Vitest bez `getViteConfig()` wystarczył: serwisy przyjmują `SupabaseClient` jako argument, więc test podaje im prawdziwego klienta konta tymczasowego zamiast mocka, a redirecty, `?error=` i middleware sprawdza HTTP na działającym dev. Astro i adapter Cloudflare nie trafiają do runnera.
- Wyrocznią jest stan bazy obserwowany kluczem admina (zbiory id, wiersze konta), a dla izolacji odpowiedź dla losowego uuid — nigdy wartość zwracana przez testowany kod ani tekst błędu przepisany z kodu.
- Zapis do lokalnej bazy dev jest dopuszczalny tylko pod wąskim wzorcem kont, którego wąskość ma własny test (`tests/harness/accounts.test.ts`), ze sweepem przed i po i porównaniem hashy. Serwerowe potwierdzenie usunięcia i F2 zostały świadomie poza zakresem (potwierdzenie w UI, test sekwencyjny).

**§3 Phase 2 — Wyszukiwanie i najlepszy (2026-11-13)**

- Wydzielenie reguł strony do `src/lib/search-view.ts` (test-first, bez zmiany wyników) dało tanią warstwę unit; HTTP (`tests/http/search.test.ts`) sprawdza już tylko to, czego unit nie widzi: nagłówek `Set-Cookie` z atrybutami i render stanów. Celowe zepsucie (`cookieMode ?? urlMode`) oblało oba poziomy.
- Regułę „najlepszego” pod współbieżnością dowodzi zachowanie: przeplot sterowany `pg_blocking_pids` plus kontrola mutacyjna w `pg_temp` (5 przebiegów z rzędu deterministycznie). Strażnik regex na treści funkcji w `supabase/tests/delete-entries.sql` zostaje jako tani sygnał w bramce pgTAP.
- Limit auth lokalnego stosu `sign_in_sign_ups = 30` na 5 min (`supabase/config.toml`): konta w `beforeAll`, jedno–dwa na plik, mało logowań HTTP; inaczej kolejne przebiegi z rzędu padają na rejestracji.

**§3 Phase 3 — Bezpieczne migracje (2026-11-19)**

- Izolacja osobną bazą w tym samym klastrze, nie schematem: migracje kwalifikują `public.` na sztywno, a rola `postgres` pod `DB_URL` ma `CREATEDB`. Bazę wyjściową (migracje do linii bazowej + fixture) buduje się raz i klonuje `template`, co wymaga zamknięcia wszystkich połączeń z nią; zastępczy `auth` ma tylko to, czego używają migracje.
- Pułapki Supabase CLI 2.117.0: `--workdir` musi wskazywać rodzica `supabase/` (inaczej cichy sukces `{"applied":[]}`), każde wywołanie dostaje wszystkie pliki już zapisane w bazie plus nowy, a pod agentem AI stdout przechodzi na JSON (`--agent no`). Plik migracji okazał się atomowy — zmierzone i przypięte testem, nie przyjęte z dokumentacji.
- `migrations` biegnie w `npm test` drugim przebiegiem: równolegle z `services` `npx supabase status` zbliżał się do limitu 60 s i `harnessEnv()` padał jako STACK_DOWN, a `catch` gubił przyczynę (naprawione w `tests/harness/env.ts`). Przebieg migracji trwa ok. 40 s, głównie wywołania CLI.

## 7. What We Deliberately Don't Test

Exclusions agreed during the rollout (Phase 2 interview, Q5). Future
contributors should respect these unless the underlying assumption changes.

- **Kitchen sink (`/dev/kitchen-sink`)** — strona tylko deweloperska, w produkcji 404. Re-evaluate if zacznie trafiać do produkcji albo stanie się źródłem regresji w komponentach. (Source: Phase 2 interview Q5.)
- **Multimodalny przegląd wizualny i snapshoty wyglądu** — wygląd zmienia się często, koszt utrzymania przewyższa sygnał przy jednym użytkowniku. Re-evaluate if pojawi się regresja wizualna, której nie złapał `lint:ui`. (Source: rewizja briefu, cost × signal.)
- **Składanie diakrytyków w wyszukiwaniu** — „maka” nie znajduje „mąka”; dopasowanie ignoruje wielkość liter i nadmiarowe spacje (klucz nazwy), ale polskie znaki muszą się zgadzać. Znane ograniczenie, nie wymóg PRD (FR-004, FR-005). Re-evaluate if PRD doda wyszukiwanie bez polskich znaków albo użytkownik zgłosi brak trafień przez pominięte ogonki. (Source: §3 Phase 2, plan testing-search-and-best, „What We're NOT Doing”.)
- **Normalizacja Unicode (NFC) nazw** — nazwa zapisana w NFD („a” + łączący ogonek) nie pasuje do zapytania w NFC („ą”). Dzisiejsze zachowanie przypina wiersz „known limitation” w `tests/unit/search-match.test.ts`. Re-evaluate if nazwy zaczną trafiać z importu albo z innych systemów (wklejanie z macOS, API), albo jeśli normalizacja zostanie dodana — wtedy ten wiersz zmienia się świadomie. (Source: §3 Phase 2, plan testing-search-and-best.)
- **Znaki zerowej szerokości w nazwach** — znak zerowej szerokości w nazwie (np. U+200B) nie jest białym znakiem dla `\s`, więc `normalizeName` go zostawia. `"Mą\u200bka"` wygląda jak „Mąka”, ale ma inny klucz nazwy, więc może powstać wizualny duplikat składnika albo zamiennika. Dzisiejsze zachowanie przypinają wiersze „known limitation” (`PINNED CURRENT BEHAVIOUR, NOT A REQUIREMENT`) w `tests/unit/entry-fields.test.ts`. Re-evaluate if nazwy zaczną trafiać z importu albo wklejania z innych systemów (strony WWW, edytory, API), albo jeśli usuwanie takich znaków zostanie dodane — wtedy te wiersze zmieniają się świadomie. (Source: §3 Phase 4, plan testing-validation-and-gates.)
- **Limit 1000 wierszy w wyszukiwaniu** — `listIngredients` nie ma paginacji, a PostgREST zwraca najwyżej `max_rows = 1000` wierszy (`supabase/config.toml`); wyszukiwanie filtruje tę listę w pamięci, więc składnik spoza pierwszego tysiąca (wg `name_key`) nie zostanie znaleziony. Przyjęte ograniczenie S-03, bez testu. Re-evaluate if którekolwiek konto zbliży się do kilkuset składników albo zmieni się `max_rows` lub sposób wyszukiwania (zapytanie w bazie, paginacja). (Source: §3 Phase 2, plan testing-search-and-best; archive/2026-10-12-ingredient-name-search.)
- **Przeploty c i e zamiany „najlepszego”** — zamiana zatwierdzona, potem usunięcie (para bez najlepszego) oraz usunięcie poprzedniego najlepszego w trakcie zamiany. Oba kończą się stanem dozwolonym bez fałszywego sukcesu, więc nie rozróżniają wersji funkcji. Re-evaluate if reguła zmieni się tak, że para musi zawsze mieć najlepszego. (Source: §3 Phase 2, plan testing-search-and-best.)
- **Atomowość „dodaj z checkboxem najlepszy”** — insert zamiennika i wywołanie `set_best_substitute` to dwa wywołania; gdy oznaczenie się nie uda, zamiennik zostaje bez oznaczenia, a użytkownik dostaje komunikat „Zamiennik zapisany, ale nie udało się oznaczyć go jako najlepszy.” (zaakceptowane w archive/2026-10-11-best-substitute-highlight). Re-evaluate if ten komunikat zacznie się pojawiać w praktyce albo dodawanie z oznaczeniem trafi do jednej funkcji bazy. (Source: §3 Phase 2, plan testing-search-and-best.)
- **Wierność zastępczego `auth` w teście migracji** — jednorazowa baza ma tylko `auth.users (id, email)` i `auth.uid()` (ciało jak w lokalnym stosie), bez reszty schematu `auth`, `storage`, rozszerzeń i uprawnień ról Supabase; test nie sprawdza też RLS ani uprawnień po migracji (to pgTAP, §6.3). Migracja, która sięgnie po brakujący element, padnie głośno w bramce, a nie przejdzie po cichu. Re-evaluate if migracja dotknie `auth`, `storage` albo rozszerzeń — wtedy decyzja o osobnym kontenerze Supabase dla testu migracji. (Source: §3 Phase 3, plan testing-safe-migrations, „What We're NOT Doing”.)
- **Polecenia globalne dla klastra w teście migracji** — role (`create/alter/drop role`, członkostwo `grant <rola> to <rola>`), `alter system`, `alter database` innej bazy i tablespace'y działają na cały lokalny klaster, nie na jednorazową bazę: migracja z nimi zmieni klaster deweloperski, a hash danych dev (`devSnapshot`) tego nie zobaczy. Uprawnienia do obiektów (`grant select on … to authenticated`) zostają w jednorazowej bazie. Dzisiejsze migracje takich poleceń nie mają (grep 2026-11-20). Re-evaluate if migracja doda takie polecenie — wtedy osobny kontener Postgresa dla testu migracji albo ręczny przegląd przed `npm run test:migrations`. (Source: impl-review testing-safe-migrations F8.)
- **Historia migracji przed linią bazową** — migracje ≤ `BASELINE_MIGRATION` (m.in. usuwanie duplikatów `20261010115230` i zmiana nazw kategorii `20261028120000`) są już na produkcji i nie mają testu na danych; fixture wstawia się dopiero po nich. Ich kształt (usuwanie wierszy, zmiana kategorii) odtwarzają syntetyczne mutanty kontroli mutacyjnej. Re-evaluate if trzeba będzie odbudować bazę od zera z danymi albo cofnąć produkcję przed linię bazową. (Source: §3 Phase 3, plan testing-safe-migrations, „What We're NOT Doing”.)
- **Atomowość pliku migracji przypięta dla Supabase CLI 2.117.0** — przypadek „a migration that fails halfway through its file leaves no trace” utrwala zmierzone zachowanie tej wersji CLI (plik w jednej transakcji), nie gwarancję z dokumentacji ani zachowanie innych wersji. Re-evaluate if aktualizacja pakietu `supabase` w devDependencies zmieni wynik tego przypadku — czerwony to decyzja (np. jawne transakcje w migracjach, przypięcie wersji CLI), nie zmiana asercji. (Source: §3 Phase 3, plan testing-safe-migrations, commit 1635024.)
